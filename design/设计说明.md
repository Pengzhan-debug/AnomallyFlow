# QualityFlow AI 2.0 界面设计初稿

依据 `QualityFlow_AI_2.0_产品需求文档_PRD_V1.0.docx` 的 MVP V1.0 范围。本文和原型是产品设计稿；原型中的批次、检测值、证据和人员均为演示数据，不表示系统已接入生产服务。

## 设计目标

让质检员能快速发起检测并找到任务，让质量工程师能在充分阅读原图、检测结果和证据后作出审批决定，让处理人能在同一条任务链上完成工单、复检与关闭。所有关键结果都保留来源、版本和状态。

## 信息架构

| 一级入口 | 主要内容 | MVP 角色 |
| --- | --- | --- |
| 任务总览 | 指标、状态筛选、任务列表、任务进度 | 质检员、工程师、主管 |
| 新建检测 | 产品和批次、单图上传、校验反馈 | 质检员 |
| 检测详情 | 原图/异常定位、分数、模型版本、执行轨迹 | 授权用户 |
| 调查报告 | 观察事实、原因假设、证据、缺失信息、检查建议 | 工程师、主管 |
| 审批中心 | 待审队列、报告版本、审批动作和意见 | 工程师、主管 |
| 工单中心 | 指派、处理、复检、关闭及事件历史 | 质检员、工程师、主管 |
| 审计记录 | 按任务串联关键事件和工具调用 | 审计员、授权用户 |

知识库管理和统计看板为 PRD 的 V1.5 范围，本轮只在导航中预留入口，不作为 MVP 完成项。

## 主流程

1. 质检员在新建检测中选择产品、批次并上传 JPG/PNG 单图。页面先校验必填字段、类型和 20 MB 上限；服务端仍须独立校验内容和批次归属。
2. 创建后进入检测详情。进度展示校验、检测、调查和审批节点。`NORMAL` 可信结果进入已完成；`ABNORMAL`、`UNCERTAIN` 进入调查；`ERROR` 明确进入需人工处理。
3. 工程师在报告中先看观察事实，再看原因假设及支持/反对证据。异常分数只标为模型分数，不展示为概率。每条证据能查看 ID、来源、版本与采集时间。
4. 审批中心提供批准、驳回、退回补证。批准前写清将创建正式工单；高风险任务需二次确认。审批版本与意见固定留存。
5. 工单经分派、处理、待复检、关闭；复检不合格返回处理中，并保留前一轮处置记录。

## 状态与文案规则

| 系统状态 | 界面文案 | 用户下一步 |
| --- | --- | --- |
| `NORMAL` | 正常检测 | 查看检测记录；可申请人工复核 |
| `ABNORMAL` | 发现异常 | 查看调查报告与证据 |
| `UNCERTAIN` | 结果不确定 | 人工复核；不能自动放行 |
| `ERROR` / `NEEDS_REVIEW` | 检测失败／需人工处理 | 查看原因并发起受控重试 |
| `WAITING_APPROVAL` | 待审批 | 工程师审阅报告版本 |
| `REJECTED` | 已驳回 | 查看原因；可发起新版调查 |

报告中的“观察事实”“原因假设”“建议检查”“人工确认”使用不同标题和标签。证据不足时在假设前展示醒目的缺失信息，避免把推断视觉上呈现为定论。

## 视觉与交互约定

- 桌面优先，左侧稳定导航、顶部任务上下文、主区单一阅读主线。窄屏时导航收起成横向入口。
- 中性深蓝作为框架色，青色代表可操作链接；琥珀色表示不确定或待审，红色仅用于异常/失败，绿色仅用于已完成。
- 卡片以轻边框和留白组织信息。重要数字必须有文字单位和含义；风险级别与检测状态不能只靠颜色表达。
- 每个关键动作都有即时反馈。审批弹窗写明任务、报告版本、决定及后果；表单错误贴近字段显示。
- 演示原型的按钮只改变本地模拟状态，不代表 API、权限或幂等规则已实现。
