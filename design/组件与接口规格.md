# QualityFlow AI 2.0 MVP 组件与接口规格 D0.1

依据 PRD V1.0 与四轮设计原型形成的前后端对接草案。账户、检测上传、审批和工单复检的首批接口已落地；本文件中的其余字段仍是建议契约，联调前需确认错误码、权限策略和资源范围。

## 1. 页面与组件边界

| 页面 | 主要组件 | 输入 | 用户操作 | 必须覆盖的状态 |
| --- | --- | --- | --- | --- |
| 登录 | `LoginForm` | 账号、密码 | 登录、密码显隐 | 缺字段、凭据错误、会话过期、无权限、服务失败 |
| 任务总览 | `TaskFilters`、`TaskTable`、`TaskStatusBadge` | 筛选参数、任务列表 | 筛选、搜索、进入任务 | 加载、空列表、筛选无结果、网络错误 |
| 新建检测 | `InspectionForm`、`ImageUpload` | 产品、批次、图像、备注 | 提交 | 本地校验、上传中、创建成功、幂等返回、服务错误 |
| 检测详情 | `DetectionViewer`、`TaskTrace` | 任务、检测结果、事件 | 原图/热力图切换、报告跳转 | 正常、异常、不确定、错误、证据核验失败、调查超预算 |
| 调查报告 | `ReportFacts`、`HypothesisCard`、`EvidenceDrawer` | 报告版本、证据索引 | 查看证据与缺失信息 | 证据充分/不足、引用失效、历史版本 |
| 审批中心 | `ApprovalQueue`、`ApprovalDecision`、`ReportVersionCompare` | 待审队列、报告版本 | 批准、驳回、退回补证 | 待审、已决定、旧版本冲突、无权限 |
| 工单中心 | `WorkOrderList`、`WorkOrderTimeline`、`AssignmentForm`、`HandlingForm` | 工单、处置和事件 | 分派、处理、查看历史 | 开放、处理中、待复检、返工、已关闭 |
| 提交复检 | `ReinspectionForm` | 工单、图像、质检员结论 | 提交复检 | 文件错误、提交中、已提交、状态冲突 |
| 用户与权限 | `UserTable`、`UserEditor` | 用户、角色、状态 | 添加、调整角色、启停 | 加载、权限不足、账号冲突、修改成功 |
| 审计记录 | `AuditTimeline` | task_id、trace_id、事件 | 查看来源事件 | 空结果、数据脱敏、权限不足 |

组件应接收业务状态和权限能力作为输入。按钮是否可见是交互表达；实际授权以每次 API 的服务端校验为准。

## 2. 通用状态与错误

列表和详情页面统一使用 `idle → loading → success / empty / error`。`empty` 表示请求成功但没有资源，`error` 表示请求失败，两者不能合并。写命令使用 `idle → submitting → success / validation_error / conflict / forbidden / error`。请求期间按钮禁用并防止重复点击；服务端仍须依靠幂等键和状态条件更新保证正确性。

建议错误响应：

```json
{
  "error_code": "APPROVAL_VERSION_CONFLICT",
  "message": "审批状态已变化，请重新查看最新版本",
  "details": { "current_version": 3 },
  "trace_id": "trc-example"
}
```

前端只显示安全的 `message` 和 `trace_id`。错误码驱动恢复动作，不能依据服务器原始异常文本拼接 UI。建议的映射如下：

| HTTP / 错误码 | 界面反馈 | 恢复动作 |
| --- | --- | --- |
| 401 / `UNAUTHENTICATED` | 会话失效 | 保存非敏感页面位置，返回登录 |
| 403 / `FORBIDDEN` | 当前角色无权限 | 不展示受限数据，提供管理员联系方向 |
| 409 / `VERSION_CONFLICT` | 数据已被他人更新 | 重新读取最新版本，再由用户决定 |
| 409 / `IDEMPOTENCY_KEY_REUSED` | 相同键对应不同请求 | 提示重新发起，不静默复用旧结果 |
| 422 / `VALIDATION_ERROR` | 字段或文件不符合要求 | 在具体字段旁展示安全错误 |
| 503 / `DEPENDENCY_UNAVAILABLE` | 检测或业务服务不可用 | 保留任务及追踪 ID，支持受控重试 |

## 3. 核心数据类型草案

```ts
type DetectionStatus = 'NORMAL' | 'ABNORMAL' | 'UNCERTAIN' | 'ERROR';
type TaskStatus =
  | 'PENDING' | 'VALIDATING' | 'DETECTING' | 'INVESTIGATING'
  | 'WAITING_APPROVAL' | 'ORDER_CREATED' | 'COMPLETED'
  | 'NEEDS_REVIEW' | 'FAILED' | 'REJECTED' | 'CANCELLED';
type ApprovalStatus = 'PENDING' | 'APPROVED' | 'REJECTED' | 'RETURNED' | 'EXPIRED';
type WorkOrderStatus = 'OPEN' | 'ASSIGNED' | 'IN_PROGRESS' | 'PENDING_REINSPECTION' | 'CLOSED' | 'CANCELLED';

interface DetectionFinding {
  status: DetectionStatus;
  anomaly_score: number | null; // 模型分数，不是概率
  anomaly_map_url: string | null; // 授权后的短期 URL
  defect_label: string | null;
  confidence_note: string | null;
  model_version: string;
  threshold_version: string;
  inference_ms: number | null;
}

interface EvidenceRef {
  evidence_id: string;
  source_type: 'detection' | 'batch' | 'inspection_history' | 'case' | 'sop' | 'supplement' | 'equipment_log' | 'reinspection';
  source_id: string;
  source_version: string;
  retrieved_at: string; // 带时区 ISO 8601
  title: string;
  excerpt: string | null;
  validity: 'CURRENT' | 'HISTORICAL' | 'INVALID';
}

interface ReportHypothesis {
  cause: string;
  supporting_evidence_ids: string[];
  contradicting_evidence_ids: string[];
  uncertainty: string;
  verification_plan: string;
}

interface InvestigationReport {
  report_id: string;
  task_id: string;
  report_version: number;
  defect_summary: string;
  observed_facts: Array<{ text: string; evidence_ids: string[] }>;
  hypotheses: ReportHypothesis[];
  missing_evidence: string[];
  recommended_actions: string[];
  risk_level: 'LOW' | 'MEDIUM' | 'HIGH';
  evidence_sufficient: boolean;
  model_version: string;
  prompt_version: string;
  generated_at: string;
}
```

`observed_facts` 中的每条事实建议显式关联证据 ID，以支持点击来源与自动核验；PRD 的初版字段可在后端确认后调整。`EvidenceRef.validity` 用于界面表达，正式有效性以服务端核验结果为准。

## 4. 关键请求与响应

### 创建检测任务

`POST /api/v1/inspections`：multipart 包含 `batch_id`、`product_code`、`image`、可选 `remark`；请求头传 `Idempotency-Key`。成功返回 HTTP 202：

```json
{ "task_id": "QI-240817", "status": "PENDING", "trace_id": "trc-example" }
```

重复的相同请求返回同一 `task_id`；请求指纹不同则返回冲突。前端取得 `task_id` 后进入详情页，通过查询或 SSE 展示进度，不等待检测完成才显示确认。

当前模拟调查会在异常或不确定检测后生成报告与审批请求。`GET /api/v1/inspections/{task_id}` 返回 `report_id`、`approval_id`、`work_order_id`；`GET /api/v1/inspections/{task_id}/report` 返回结构化报告，`GET /api/v1/inspections/{task_id}/evidence/{evidence_id}` 返回证据来源和版本。报告可引用检测结果、批次和实际检索到的 SOP/案例，不把假设写成已确认根因。引用失效时任务进入 `NEEDS_REVIEW`，不产生可审批报告。

实现已加入 SOP/案例/历史检测证据引用及 `tool_trace`：`POST /api/v1/inspections/{task_id}/tools` 接收 `tool_name` 和白名单 `arguments`，仅工程师/主管可手动调用；`GET` 同一路径读取持久化调用记录。租户、产品、任务上下文由服务端注入。检索仍为本地字符向量；调查可选固定计划或真实 DeepSeek Agent，后者已支持 LangGraph 节点 checkpoint 和审批恢复。`inspection_history` 类型证据标记为 `HISTORICAL`，不能视作本任务的检测结论。

### 已落地的报告版本与补证接口（2026-11-02）

| 接口 | 行为 |
| --- | --- |
| `GET /inspections/{id}/reports` | 列出不可变报告版本、对应审批与决定 |
| `GET /inspections/{id}/report?version=N` | 读取指定版本，不传则取最新已发布报告；包含对应 approval_id/status |
| `GET /inspections/{id}/supplements` | 列出各轮补证与回应的退回审批 |
| `POST /inspections/{id}/supplements` | 原任务质检员提交 image、note、expected_version、expected_report_version 和 Idempotency-Key；202 返回材料和新报告目标版本 |
| `GET /inspections/{id}/image` | 受保护原始检测图像 |
| `GET /inspections/{id}/supplements/{supplement_id}/image` | 受保护补证图像 |

上述路径均以 `/api/v1` 为前缀。补证只接受当前已退回报告，同键同内容重试返回原记录，改内容 409，并发只能增加一个版本。任务详情用 `current_report_version` 表示已入队目标，`latest_report_version` 表示已发布版本，两者可能暂时不同；前端应标明正在查看历史报告。报告版本切换时审批详情须同步切换。新一轮入队后旧审批返回 409，不能复用旧批准意见。

工具日志包含 `report_version`，`GET /inspections/{id}/tools?version=N` 可按轮查询。本轮材料为 `supplement` 证据，新版引用必须绑定相同任务、版本与内容哈希。图像保存供人工核验，暂不自动复检补证像素。

### 已落地的视觉样本和检测接口（2026-11-02）

| 接口 | 行为 |
| --- | --- |
| `GET /detector` | 当前检测模式、按产品配置的模型/阈值版本；不含密钥或服务地址 |
| `GET /visual-samples?product_code=...&limit=100` | 本租户样本、总量与训练/验证/测试集的标签计数 |
| `POST /visual-samples` | 工程师/主管/管理员上传 image、product_code、label、split、source、note；201 返回样本或同内容重放 |
| `GET /visual-samples/manifest?product_code=...` | 导出全部样本元数据及清单哈希，图像路径需要认证 |
| `GET /visual-samples/{id}/image` | 本租户受保护样本图像 |
| `GET /inspections/{id}/anomaly-map` | 此任务的已验证 PNG 定位图；没有图时 404 |

样本 `label=NORMAL/ABNORMAL`，`split=TRAIN/VALIDATION/TEST`；TRAIN 只接受 NORMAL。同租户同一文件禁止跨产品/标签/划分重复登记，精确重试不新增。样本产品代码允许在生产批次建立前登记，导入不创建生产批次。样本上传不训练模型，来源与人工标签不等于模型已验证。检测结果新增 `detection` 元数据、`detector_mode` 和 `has_anomaly_map`，模式、质量、模型/阈值版本应在详情可见。规范与质量门见 [视觉检测接入](视觉检测接入.md)。

### 审批决定

`POST /api/v1/approvals/{id}/decision`：

```json
{
  "decision": "APPROVE",
  "expected_report_version": 1,
  "expected_version": 2,
  "reason": "已核对证据并要求按建议复拍抽检"
}
```

`decision` 枚举 `APPROVE / REJECT / RETURN_FOR_MORE_EVIDENCE`。成功响应返回审批 ID、阶段、状态、决定时间和版本。高风险先由工程师批准并转主管阶段，再由不同账户的主管共同批准；两阶段批准均须填写依据。只有最终批准后才允许创建工单。完整规则见 [业务规则决策](业务规则决策.md)。

### 工单命令

当前实现以 `POST /api/v1/work-orders/{id}/start` 记录工程师开始处置的原因，以 `POST /api/v1/work-orders/{id}/handling` 提交具体措施，均带 `expected_version`。完整的负责人分派、起止时间和附件仍待实现。工单状态由业务服务校验，成功返回最新版本。

复检提交 `POST /api/v1/work-orders/{id}/reinspections` 带新图像、质检员观察结论、说明和目标版本。`UNCERTAIN` 保持待复检，工程师要求补拍后质检员追加新一轮记录；不得据此关闭。工程师通过 `POST /api/v1/work-orders/{id}/reinspections/{reinspection_id}/review` 确认通过、退回处理或要求补拍，带目标工单版本和理由。失败复检返回处理中时创建新事件；原复检记录不可覆盖。

## 5. 事件流与断线恢复

SSE 事件至少包含 `event_id`、`task_id`、`event_type`、`timestamp`、`safe_payload`。界面显示校验、检测、调查、待审批和工单创建等业务节点。隐藏模型内部推理、凭据和敏感原文。

连接中断时将状态标为“连接中断，正在重新同步”；重新建立连接后先调用任务详情获取正式状态，再订阅后续事件。事件可能重复，前端按 `event_id` 去重。不能用最后一条本地事件推断审批或工单已经成功。

## 6. 版本与历史展示规则

- 报告按 `task_id + report_version` 展示，审批总是引用一个不可变报告版本。版本对比列出新增或移除证据、事实和待核实点，并保留旧审批意见。
- 工单处置按版本追加。每次复检有独立 `reinspection_id`、图像引用、质检员观察结论、工程师确认和时间。
- 返工只追加事件并回到 `IN_PROGRESS`，不能把前一轮不通过记录改成通过。
- 最终人工确认原因与 Agent 假设不一致时，显示差异标记并保存到反馈数据；不改写原报告。

## 7. 前端验收场景

1. 质检员视角看不到审批和用户管理入口；直接请求受限 API 仍需服务端返回 403。
2. 检测 `ERROR` 不展示正常分数，证据核验失败和预算超限均进入人工处理表达。
3. 任务列表“无记录”和“加载失败”有不同界面及恢复动作。
4. 切换审批队列后，右侧任务号、报告版本、证据摘要及决定状态同步改变。
5. QI-240811 的报告 v1、v2 可对比，新增证据可打开来源详情；旧退回意见仍可见。
6. WO-240802 的两轮处置和复检完整显示，第一次失败返工与第二次关闭均可追溯。
7. 管理员调整演示用户角色必须填写原因；正式实现需记录操作者、时间、前后值和 trace_id。

## 8. 已固定规则与待确认项

高风险共同审批、复检“无法判断”路由及管理员创建本地账户已按 [业务规则决策](业务规则决策.md) 固定。文件保留周期与正式环境账户会话期限仍需确定。
