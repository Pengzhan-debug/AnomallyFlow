# Agent 对照评测设计 D0.1

状态：待实现/待执行。更新：2026-11-05。配套 [Harness 接入设计](DeepSeek-Harness接入设计.md)。

本文件定义评测方法和结果格式，不新增“Agent 成功率”实测数字。仓库既有 74 项后端测试及 19 项检测/评测测试证明各自覆盖的工程行为；它们不是 93 道真实 LLM 调查能力题。PatchCore 的 AUROC、检测接口吞吐不参与 Agent 能力评分。

## 1. 评测问题与实验组

需要分别回答：

1. 系统能否控制工具、身份、预算、版本和副作用？
2. 真实模型能否选择有用查询，形成被证据支持的报告，并识别缺失信息？
3. 加入 Harness 后，质量、成本、延迟和故障恢复是否改变？

| 组别 | 执行方式 | 用途 |
| --- | --- | --- |
| E0 | 脚本化模型 + 假运行时/故障注入 | 确定性工程回归；不纳入真实模型质量分数 |
| A | 现有 LangGraph + DeepSeek | 真实模型基线 |
| B | DeepSeek Harness + 同一 DeepSeek | 候选调查后端 |
| C，可选 | 固定工具计划 + 同一 DeepSeek | 区分自主选工具与固定取证；独立报告，不混入 A/B 主结论 |

A/B 控制变量：解析后的模型版本、业务提示词、输入证据、工具名/Schema/语义、报告契约、推理参数、8 次工具/10 次模型/120 秒累计预算及输出 token 上限。记录完整模型可见提示词哈希、业务提示词哈希、profile/runtime 版本和全部额外上下文。

原接口目前通过 Anthropic 兼容协议调用，Harness 默认路由不同。若同一实际模型、思考模式或有效提示词无法对齐，结果标为“系统级方案比较”，不能把差异单独归因于 Harness。自动压缩/额外规划/自动重试等能力如要测，应另开具名实验，不能只在一组静默启用。

不要求两组逐字回答一致或走完全相同的工具顺序；检查是否完成必要取证，并统计冗余调用。

两组使用共同 EvalSupervisor，从调查输入准备完毕、首次后端启动之前开始计时，并施加相同的 120 秒墙钟上限；检测、上传和排队延迟单列，不混入调查延迟。现有 LangGraph 的内部累计计时并不覆盖全部初始化开销，不能只比较两个后端各自的计时字段。模型准入和调用计数也由共同评测适配层核对实际请求，包括失败重试；无法对齐的运行标记为不可严格比较，保留在系统可用性统计中。

## 2. 数据与标准答案

先建立 12 个开发案例及 24 个冻结测试案例，每个测试案例运行 3 次；A/B 共 144 次真实运行。数量是起步计划，不是当前已有基准。

场景覆盖至少六类：可查到直接事实、相似案例但不能确认当前根因、资料缺失、证据矛盾、过期/跨产品干扰、退回补证后的新证据。每类设置不同数据和预期证据，避免只改写同一个问题。既有 12 类业务场景可用于构建 fixture，但需另补调查任务与人工标注，不能直接把流程通过作为调查正确。

开发/测试按问题模板与数据来源族划分，分开版本；冻结测试集不用于挑提示词、阈值或工具策略。正式试验固定所有时间、资料有效期和工具快照，防止两组查到不同数据库内容。

每个案例至少包含：

| 字段 | 含义 |
| --- | --- |
| case_id / case_version / family / split | 不变身份与分组 |
| context_fixture | 产品、批次、检测结果、备注及本轮版本 |
| tool_fixtures | 工具可见事实、来源 ID/版本、有效期和空/错误结果 |
| required_evidence | 应查出的关键证据，含可接受替代来源集合 |
| acceptable_tool_goals | 可接受查询目标；不把某一固定轨迹当唯一正确答案 |
| forbidden_claims | 不能从现有证据得出的具体结论 |
| expected_missing_evidence | 必须指出的现场检查或资料缺口 |
| acceptable_hypotheses | 允许的待验证原因及不能混淆的事实 |
| minimum_risk / expected_disposition | 风险下限、应进入审批或人工处理的路径 |
| marking_notes | 标注依据、边界及人工分歧记录 |

在已确认的事实之外，允许模型提出带明确不确定性和验证计划的合理假设；不能把假设写成观察事实。业务真值来自人工编写的合成 fixture 或审核资料，不能直接采用待测模型自己生成的答案。

当前单图策略要求 evidence_sufficient=false，因此不以该标志的命中率声称模型学会了“证据充分性分类”。本阶段评价缺失项覆盖和无依据确定性结论；以后增加允许充分证据的业务场景并调整政策后，再设计双类识别指标。

## 3. 指标、分母与评分

### 3.1 工程指标：由代码判定

| 指标 | 定义 |
| --- | --- |
| 运行完成率 | 有已接纳、通过业务校验的报告运行数 / 所有启动运行数 |
| Schema 首次通过率 | 首次提交即通过 Schema 的运行数 / 所有启动运行数；另报最终通过率与修正次数 |
| 来源身份有效率 | 可定位且满足任务/租户/版本/时效政策的实际引用数 / 全部实际引用数 |
| 越权拦截率 | 明确拒绝的注入越权尝试 / 注入越权尝试总数 |
| 重复正式副作用数 | 每个审批/报告唯一键下多出的正式报告、审批或工单数量 |
| 旧凭证成功数 | 已过期或被替代 generation 仍成功执行/发布的次数 |
| 恢复成功率 | 指定中断点后恢复至预期正式状态且无重复结果的运行数 / 全部中断运行数 |

没有引用时来源有效率为 N/A，不能记为 100%；整体报告质量和完成率仍按该运行评分。没有提交报告或运行失败，不能从完成率和任务成功率分母中删除。工具返回 ERROR 或空结果时运行可以正确报告不足，但不能声称工具查到了事实。

### 3.2 调查质量：代码与人工结合

| 指标 | 评分口径 |
| --- | --- |
| 关键证据召回 | 找到的 required_evidence 单元 / 该案例应找出的证据单元；按案例宏平均 |
| 工具目标完成率 | 完成的必要取证目标 / 必要目标总数；接受不同顺序及等价工具路径 |
| 事实支持率 | 被引用原文/结构化事实实际支持的 observed_facts 原子断言数 / 所有 observed_facts 原子断言数 |
| 无依据确定结论率 | 将假设或无来源断言写成确定事实的报告数 / 所有有效报告数；同时报告失败运行比例 |
| 缺失项覆盖 | 正确指出的预期缺失证据项 / 应指出项；允许明确等价表述 |
| 假设可验证性 | 每个假设是否关联支持/反证或明确来源不足，且验证步骤可以实际执行 |
| 任务成功率 | 所有启动运行中，既通过工程校验，又满足关键证据、必需缺失项、风险与禁止结论规则的运行比例 |

空事实列表、没有有效报告时不得通过“没有幻觉”获得高分。事实支持需查阅来源内容，不能只检查 ID 是否存在。评审者对两组输出隐藏后端名称；人工按冻结 rubric 标注关键项目。LLM-as-judge 可用于辅助筛选，但需记录评审模型、提示词和人工抽检，不作为唯一业务真值。

建议先分别展示各项，不用未经论证的权重加成一个总分。

### 3.3 效率与成本

每次运行记录：总墙钟、模型请求数（包含重试/额外请求）、只读工具次数、唯一有用调用数、格式修正次数、模型各阶段 token 用量、缓存 token 计费口径、工具耗时、SDK 启动时间和安全错误码。

报告成功和失败运行的延迟分布，并另列全体 p50/p95、超时比例及平均调用数。固定 120 秒的超时运行仍进入全体统计，不能只展示成功者延迟。

费用依据实际供应商 usage 和冻结价格表计算，注明币种、计价日期和缓存规则；无法获取的字段记 null，不能记 0。包含单独的初始化/框架附加请求成本；同时报告冷启动与复用进程的条件。P0 一 run 一进程，不将后续进程池的设想算成已实现收益。

## 4. 执行与隔离协议

1. 生成冻结数据快照和 manifest 哈希；A/B 从同一快照创建独立运行数据库或命名空间。
2. 历史工具只看到 fixture 指定的历史；本轮生成的报告/任务不得成为后续案例的可检索历史，防止数据污染。
3. 预先固定运行次序种子，交错执行 A/B；每个 case/repeat 使用新 session、隔离 home 和相同时间锚点。
4. 只运行真实模型；假模型结果保存在 E0 独立目录。模型使用相同可控参数，记录不能固定的参数。
5. 每个 case 的重复运行用于估计稳定性；CI/差异统计按 case 分组，不能将同一案例三次重复当作独立案例样本。
6. 冻结 rubric 后才评审；报告失败案例、空检索案例和超时，不因其拉低分数而删掉。
7. 测试集启动后不能因某个结果不佳再修改提示词后沿用同一试验标签；改动需产生新版本实验，并保留原结果。

结果写入 reports/agent-eval/<experiment_id>/，建议结构：

```text
manifest.json              # 数据、代码、模型、runtime、profile、工具、提示词和价格版本
cases/<case_id>.json        # 冻结标注或其内容哈希/可获取位置
runs/<backend>/<case>/<n>.json
judgments.jsonl            # 事实支持、缺失项、禁止断言等判定及依据
summary.json
summary.md
```

运行 JSON 的最小字段：case_id、repeat、backend、attempt/run/session 标识、模型解析版本、状态/错误码、原始报告草稿、正式校验结果、调用与证据快照、计时/token/费用（可空）、业务副作用数量、fixture 和配置哈希。令牌、模型密钥和内部授权头不得进入公开报告。

## 5. 恢复与防重专项矩阵

| 注入点 | 必须验证 |
| --- | --- |
| 准备提交后、SDK 启动前 | 新 Worker 能接手，旧 token 失效 |
| 工具结果提交后、回复模型前 | 同调用 ID 重放得到同一结果，不重复扣预算 |
| 草稿暂存后、正式发布前 | 恢复后发布既有草稿，不重新调用模型 |
| 正式报告事务提交后、队列回执丢失 | 同一版本只有一份正式报告/审批 |
| 模型运行期间到达 120 秒截止时间 | run 能力撤销，进程退出或隔离，迟到调用无法写入 |
| 旧 run 仍发送回调，新 generation 已接手 | 所有旧调用及报告被拒绝 |
| 工程师已批准、等待主管期间重启 | 正式审批阶段不回退，不能重复调查 |
| 退回后新版本已入队 | 旧会话不能提交到新版本；新版本独立证据/会话 |

此矩阵在 SQLite 做功能验证，同时必须在 PostgreSQL 验证 HTTP 回调、外键写入与锁等待；只用 SQLite 的通过结果不能证明不存在 PostgreSQL 回调阻塞。

## 6. 开放门槛与结论规则

以下是拟定工程门槛，尚无本轮实测结果：

- 既有工程回归保持通过，新网关和恢复矩阵通过。
- 越权执行、旧凭证成功、无审批创建正式工单、重复正式工单均为 0。
- profile 白名单、预算覆盖、取消退出及工具身份探针全部通过。
- A/B 报告包含完整失败分母与案例级结果；所有成本未知项有原因。
- 不预设 Harness 会提升质量或速度。样本不足或置信区间较宽时，结论只能是可行性/趋势；未证明收益不更换默认后端。
- 性能和成本若有差异，先核对模型、提示词、协议、缓存与数据一致性，再讨论框架贡献。

评测报告必须区分“预期目标”“确定性测试结果”“真实模型实测”“真实生产验证”。合成质量案例的分数不代表真实产线调查效果。
